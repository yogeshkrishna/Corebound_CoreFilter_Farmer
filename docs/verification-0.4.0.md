# Verification for 0.4.0

Verified on Windows on 4 October 2026 using the pinned JDK 17, Android SDK 35 and Gradle 8.9 toolchain. No additional videos were opened or analysed for this overhaul. Existing small image fixtures were run automatically as regressions.

## Completed checks

- `tools/build.ps1`: APK assembly, **151 JUnit/Robolectric tests**, Android lint, **183 pixel-recognition assertions**, and **24 navigation replay assertions** passed. Lint reports existing/nonfatal platform warnings; there are no lint errors.
- Generated closed-loop worlds: ordinary forward traversal reached its exit without air Hookshots or roof collisions; an S-shaped rectangular world completed two drops and two committed direction changes. These worlds use simplified ballistic physics, not Corebound's engine.
- Controller cases: rear enemies cannot override entrance movement; visible roofs do not trigger extra air pulses; high-roof scouting waits for the current ascent; occluded ceilings do not count as inspected; a forward wall does not suppress a named rear return; a zero ordinary count retains hanging candidates; a positive count starts a return search without a detected enemy; a moving return continues past ten seconds; a stalled return does not count as a completed sweep.
- Perception cases: decorative triangular strips and picture borders do not become collision terrain; rectangular stepped roofs, thin platforms and a textured wall under coloured illumination retain evidence. Camera tests cover signed movement, reversals, vertical displacement, occlusion, independent deformation and explicit lost-registration reanchoring. Weak foot evidence requires registered stationary support; falling or blank-camera views do not confirm a landing.
- Run/map cases: finish snapshots are captured once before reset, defeats retain their maps, crate/ad stages cannot duplicate a map, and only actual Play/Retry actions request a camera reset. Map persistence tests exercise PNG signatures/chunk checksums/inflation, raw JSON fields, geometry colours, authenticated transfer, path rejection, incorrect receipts, interrupted downloads and the matching-hash deletion path.
- `node tools/test-map-receiver.mjs`: **six Windows receiver integration scenarios** passed: valid download, corrupt contents, truncated contents, already-saved file, conflicting existing file and invalid metadata. The test checks the actual saved bytes before the receipt arrives. The browser checksum fallback also matched SHA-256 for **five generated vectors**. The bundled receiver and repository helper are byte-identical. These checks run in the release workflow before publication.

## Changed regression contracts

The old planner assumed every recorded camera view could be registered and that grey pixels under obscured feet proved a landing. The new tests distinguish a weak foot candidate from confirmed support, and require an uncertain view to retain the camera anchor and leave terrain/path records unchanged. The recorded manual sequence contains one registered transition followed by three effect-obscured views; it is not presented as evidence of uninterrupted camera tracking. Generated tests separately verify signed drops, grounded-support fusion and direction changes.

Other intentional changes include a 350 ms minimum default jump spacing, entrance priority, visibility-based ceiling inspection, release instead of blind direction reversal, and removal of a gate-animation deadline. Assertions around those contracts were updated alongside new failure cases and closed-loop coverage.

## Practical limits

There has been no live run on the user's phone with 0.4.0. APK assembly and tests do not prove complete real-level geometry, correct perception in every frame, every Spectrum kill, unattended repeat farming, ad handling for new creatives, or an improved filters-per-hour rate. The local transfer has been exercised through loopback HTTP and Android tests; the user's actual Wi-Fi topology still needs a phone/laptop trial.

No real completed-level picture has been generated by this version yet. After the first cleared or failed run, the phone queues a ZIP containing `map.png` and `map.json`. Missing observations remain unknown, unlinked coordinates use separate panels, and run success is recorded independently of map completeness. Layout-pool identification and route reuse are intentionally deferred.
